# Event pricing pipeline: take-home exercise

You've inherited a small batch pipeline from a colleague who has moved teams. Every morning it forecasts daily ticket demand for events that are on sale and recommends a price change for each event and seating tier. The business team reads the output CSV before 8am and decides which changes to apply.

It runs, the output looks reasonable at a glance, and most of the tests pass. Your job is to work out whether it can be trusted, fix what matters most, and explain your reasoning.

All data is synthetic. The events, prices and traffic are generated by `make_data.py` with a fixed seed, so you and we see identical numbers.

## What's here

```
make_data.py              generates the CSVs in data/ (deterministic)
data/
  events.csv              one row per event and tier: show date, capacity, base price
  sales.csv               daily tickets sold and selling price per event and tier
  web_traffic.csv         daily web sessions per event, from the analytics export
  inventory_snapshot.json what the mocked inventory service serves
pipeline/
  ingest.py               load and join the sources
  features.py             feature engineering
  model.py                train the demand model, validation metric
  pricing.py              forecast -> recommended price
  inventory_client.py     client for the inventory service, plus a flaky local mock
  run.py                  entry point
tests/                    pytest suite
```

Flow: `ingest` → `features` → `model` (forecast tomorrow's demand per event/tier) → `pricing` (fetch live remaining seats and current price from the inventory service, project sell-through, recommend a price) → `output/recommendations_<date>.csv`.

The inventory service is mocked locally (`MockInventoryAPI`), but treat it as a real remote dependency: it times out and returns errors some of the time, and its responses reflect the current state, not the state on any past date.

## Setup

Python 3.10 or later. Either:

```bash
uv sync
uv run python make_data.py
uv run python -m pipeline.run
uv run pytest
```

or, with pip:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python make_data.py
python -m pipeline.run
pytest
```

`python -m pipeline.run --help` lists the options (`--as-of` reruns for an earlier day; `-v` shows per-request logging).

## Your tasks

You don't need to finish everything. Deciding what to leave out is part of the exercise, and we'd rather see four things done well than eight done badly.

1. **Get it running.** List every problem you find, ranked by severity, with how you found each one.
2. **Fix the ones you think matter most.** Add a regression test for each fix: it should fail on the original code and pass on yours.
3. **Evaluate the forecast honestly** against a simple baseline (for example, the same day last week) and report the result, including if the model doesn't beat it.
4. **Add one guardrail and one monitoring check** that would each have caught a problem you found in step 1.
5. **Stretch, optional:** generate a one-line plain-English explanation per recommendation with an LLM, plus a check that every number in the text matches the input data, and an estimate of the cost per 10,000 recommendations. Skipping this won't count against you.
6. **Write a one-page `NOTES.md`:** what you found, what you fixed, what you didn't get to and why, and what you'd do next.
7. **Add a short AI-use note** (a section in `NOTES.md` is fine): which tools you used, where they helped, where they were wrong, and how you checked their output.

## Rules

- **AI tools are allowed and expected.** Use whatever you normally use. Declare it in the AI-use note. We're interested in how you check what a tool tells you, not in whether you used one.
- **Return a git repo** (a link, or a zip including the `.git` folder) **with your commit history**. Commit as you go; please don't squash into a single commit. The repo you received already has an initial commit, so start from that.
- You don't need to make the code general or production-grade beyond what your fixes require.

## Afterwards

We'll book a follow-up call. You'll walk us through what you found and changed, we'll ask about a couple of the functions you modified, and then we'll make a small change to the requirements together, live, with your usual tools available.
